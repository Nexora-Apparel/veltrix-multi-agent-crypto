# H3.1 worker fencing implementation design

## Status and scope

This is an implementation design and code-audit artifact, not a claim that worker fencing or the pipeline has been implemented.

The design is deliberately blocked from production composition until the H1.1 worker-adapter branch is incorporated into the H2/H3 integration line and the dedicated disposable Turso conformance suite passes.

## Verified interface gap

The current `RunContext` in `veltrix/orchestration.py` carries:

- run ID and idempotency key;
- attempt number and deadline;
- item budget and monotonic clock;
- fencing token;
- a zero-argument preflight fence callback.

It does not carry the lease owner ID, lease name, or a transaction-scoped fence assertion. Its current `assert_fence()` opens a separate read/check path through `OrchestrationStore.assert_fence()`. That is useful as a checkpoint, but cannot make a worker mutation atomic with lease validation.

### Required RunContext contract

Add immutable lease identity to the context:

- `owner_id`;
- `fencing_token`;
- `lease_name` (default `global-worker`);
- a transaction assertion callback with the conceptual signature `assert_fence_in_transaction(db, now_ms=None)`.

The callback must call the same `OrchestrationStore._assert_fence_in_transaction` predicate using the supplied connection. It must not open another connection. The predicate must verify the exact lease name, owner ID, fencing token, and `expires_at_ms > now_ms`.

Keep `assert_fence()` for inexpensive preflight checkpoints, but never treat it as a substitute for the transaction-scoped assertion. Keep the context's monotonic deadline and item-budget checks independent of the database wall clock.

## Transaction and store API design

Introduce a narrowly scoped transaction helper (or equivalent worker-local pattern) that:

1. opens a connection through the shared `connect_database()` adapter;
2. sets `row_factory_for()`;
3. begins the write transaction using the backend-supported transaction semantics;
4. invokes `context.assert_fence_in_transaction(db)` before any durable mutation;
5. performs the job-state and evidence/ledger mutations on that same connection;
6. commits once, or rolls back the entire unit on any exception.

Do not use a store method that opens and commits its own connection from inside a fenced worker transaction. Add optional existing-connection parameters or explicit `*_in_transaction(db, ...)` methods to stores. The store must not commit or close a connection it does not own.

For remote Turso, transaction behavior must be proven by the dedicated remote conformance suite. Do not assume SQLite's local `BEGIN IMMEDIATE` behavior maps identically to the remote driver.

## Worker-by-worker mutation map

### Initial enrichment — `CandidateEnrichmentWorker`

- Fence the discovery-to-job insertion into `solana_enrichment_jobs`.
- Fence expired-lease recovery and candidate claim in one transaction.
- Include an owner/token or equivalent claim-generation identity in each claimed job row. The current per-job `lease_until_ms` alone is not a global fencing identity.
- Fetch market data outside the write transaction, with bounded provider timeouts and context checkpoints.
- Before persistence, reopen a transaction, assert the global fence, verify the claimed job still belongs to this attempt, insert the market snapshot, and mark the enrichment job completed atomically.
- On provider failure, fence and verify the same claim before scheduling retry/dead status.
- If the global lease is lost, stop immediately; do not call the worker's failure handler.

### Market refresh — `MarketRefreshWorker`

Apply the same claim-generation and fenced-transaction rules to `solana_market_refresh_jobs`.

The refreshed market snapshot and refresh-job success transition must be committed together. A failed provider request may schedule a retry only after the global fence and claim identity are revalidated inside that retry transaction.

### Risk evidence — `SolanaRiskEvidenceWorker`

Apply the same rules to `solana_risk_evidence_jobs`.

Risk provider reads remain outside write transactions. The append-only risk evidence insert and successful job transition must be fenced and committed atomically. A provider failure must not be persisted as a worker failure after lease loss.

### Consensus — `ConsensusWorker`

Apply the same rules to `solana_consensus_jobs`.

Market/risk reads and consensus calculation can occur outside the final write transaction, but the final transaction must revalidate the global fence and claim identity before appending the consensus decision and advancing the job schedule. A stale worker must not append a decision after a new lease owner has taken over.

### Discovery / launch ingress

The long-lived PumpPortal stream supervisor must remain outside the ephemeral one-shot runner. The one-shot discovery stage must use bounded polling/read calls. Any discovered-candidate insert and associated feed event/outage mutation must be fenced in the transaction that writes it. Audit the exact launch-store write methods before implementation; do not assume every launch-store method is a pipeline write.

### Paper-only stage

Keep disabled by default. If enabled later, the paper ledger mutation must share a transaction with the fence assertion and must verify the latest consensus decision is still eligible and sufficiently fresh. It may call only the existing paper broker/ledger. No signer, transaction builder, RPC submission, or broadcast interface may be introduced.

## Claim identity and recovery

A global lease protects the pipeline invocation, while per-row processing leases protect individual jobs. Each claimed row therefore needs a durable claim identity, preferably:

- `claimed_by_owner_id`;
- `claim_fencing_token`;
- `lease_until_ms`.

A claim mutation must write all three under the current global fence. Completion/failure/retry must match all three and require an unexpired row lease. This prevents a delayed worker from completing a row that has already been reclaimed, even if it still holds an old in-memory list of candidate IDs.

Interrupted-job recovery must itself run under the global lease and must only recover expired per-row leases. A lost global lease is not a failure result; it is a stop condition. Recovery belongs to the next valid owner.

## One-shot composition

After worker contracts are implemented, compose exactly this order:

1. bounded discovery;
2. initial enrichment;
3. market refresh;
4. risk evidence;
5. consensus;
6. optional paper review/execution, disabled unless explicitly configured.

Pass one active `RunContext` through every stage. Check the deadline and item budget before each bounded unit and before/after provider calls. Provider timeouts must fit within the remaining deadline. Defer retries to a later scheduler invocation; do not add in-process retry loops.

Return a sanitized aggregate report keyed by run ID, with per-stage discovered/claimed/processed/succeeded/failed/deferred counts. Do not include secrets, raw provider bodies, or arbitrary exception messages.

## Required regression tests

For every worker and every mutation category (claim, complete, failure, retry, evidence write):

- valid owner/token succeeds;
- stale token is rejected before any row or evidence mutation;
- wrong owner is rejected;
- expired global lease is rejected;
- expired or superseded per-row claim is rejected;
- injected failure rolls back evidence and job transition together;
- lease loss during provider I/O prevents all subsequent writes;
- duplicate stage invocation is idempotent;
- a delayed old worker cannot complete a reclaimed job;
- deadline exhaustion defers rather than marking a false failure.

Pipeline-level tests must additionally prove strict stage order, bounded per-stage batch sizes, partial-stage failure behavior, stable idempotency-key semantics, paper-off default, and no live execution path.

## Branch and release dependencies

Current PR topology is not yet a single integration line:

- PR #17 (H1.1 adapter) is based on `work/turso-database-adapter`.
- PR #18 (H2 hardening) is based on `work/h2-bounded-orchestration`.
- PR #19 (H3 contract) is based on `work/h2-fencing-hardening`.

The H2/H3 line therefore does not automatically contain PR #17's worker adapter changes. Before implementing worker code, establish an explicit integration branch that includes the H1.1 adapter and H2 fencing hardening, resolving conflicts and rerunning the complete test suite. Do not merge sibling drafts or assume their changes are present merely because both PRs are open.

## Exit criteria

H3 worker fencing is not complete until:

1. the integration branch contains H1.1 adapter changes and H2 hardening;
2. current-head local CI passes;
3. all worker writes use transaction-scoped global and per-row fencing;
4. local worker and pipeline regression tests pass;
5. dedicated disposable Turso conformance passes;
6. full SQLite and Turso one-shot integration runs produce consistent, sanitized reports;
7. paper execution remains disabled by default and the live transaction boundary remains absent.

No deployment or production scheduler is authorized by this design document.
