# VELTRIX Multi-Agent Crypto

Paper-only research and monitoring system for Solana, Base and BSC. It has no wallet signing, private-key loading, swaps or live order execution. `LIVE_TRADING=true` is rejected.

## Current components
- Scout / Whale / Sniper: initial signal logic. Sniper now requires a typed, passing SafetyReport from the independent validator; raw booleans in market payloads are rejected. Whale-flow and verified launch-safety feeds are not yet connected.
- Shield: enforces at least two distinct BUY agents, a maximum $50 position and a maximum of 10 open positions.
- Exit: the SQLite paper broker persists 2x / 3x partial-profit milestones and stop/trailing-stop state across restarts; this is paper-fill simulation, not exchange execution.
- DexScreener adapter: read-only token-pair snapshots for Solana, Base and BSC.
- Helius Parsed Events connector: read-only Solana wallet swap history for configured tracked wallets, with token-mint matching, bounded pagination, successful-swap filtering and an injected spot-price resolver. The USD notional is an estimate using the current spot price, not the historical execution price.
- Alchemy Transfers By Wallet connector: read-only Base and BNB Chain (BSC) wallet transfer history using the multichain Data API. It emits a BUY only when the same transaction includes an inbound target ERC-20 and an outbound operator-allowlisted USDC/USDT/DAI transfer from the tracked wallet; plain transfers, deposits and airdrops are rejected. Quote notional treats the stablecoin quantity as an approximate USD value (not an exact historical execution valuation); depegs, fees, router behavior and provider labeling can affect it. Pagination is bounded, provider partial errors fail closed, and `alchemy` remains untrusted until explicitly allowlisted.
- Wallet provider factory: constructs Helius and/or Alchemy read-only connectors only when both the corresponding API key and tracked-wallet list are configured. It does not add either provider to the trust allowlist and does not enable trading.
- CrossChainIntelligenceCoordinator: fetches observations from trusted connectors, verifies that each response identifies the connector that returned it, rejects observations for the wrong requested chain, normalizes all providers in one pass and deduplicates by `(chain, wallet, transaction ID, token)` using case-insensitive EVM normalization and case-sensitive Solana base58 normalization. It then forms fresh multi-wallet clusters from the configured tracked-wallet allowlist and can enrich a token context for the Whale agent. Provider failures are isolated and reported without exposing credential-bearing exception details. `Core.evaluate_with_intelligence()` discards caller-supplied whale claims and accepts cluster evidence only when the coordinator result matches the token chain; Core still requires same-token consensus from at least two distinct agents.
- Optional monitor integration: when API credentials, tracked wallets and provider trust allowlists are configured, the 24-hour monitor collects verified wallet observations alongside market snapshots and reports cluster/failure counts. This remains observation-only: it does not open paper positions or send live orders.
- GoPlus token-security connector: read-only BSC (chain ID 56), Base (chain ID 8453) token-risk endpoints and authenticated Solana beta endpoint. It can only mark LP liquidity locked when the returned LP-holder list is complete and every listed holder is explicitly locked. For Base and BSC, it preserves the documented `creator_percent` fraction as a separate creator-concentration field; it does not treat this as complete developer-wallet concentration. Solana creator concentration remains unknown. Developer holdings and bundled-supply evidence remain unknown to the strict Sniper validator, so GoPlus alone cannot pass the complete Sniper gate. Base and BSC creator concentration are taken from the documented `creator_percent` field when present.
- Optional candidate discovery: consumes DexScreener's latest token-profile feed, filters to configured chains, deduplicates and caps candidate counts. This is profile/promotional discovery, not an exhaustive new-pair feed or organic trend ranking.
- WhaleFlowAggregator: clusters buys only from operator-allowlisted wallets, within a freshness window and minimum-notional threshold. A real transaction/indexer feed and vetted wallet list are still required.
- Launch Intelligence Provider Layer (`veltrix.providers.launch`): `HeliusLaunchIndexer` scans Solana launch-mint activity with Parsed Events Scan pagination, filters parsed swaps and records launch-window token receipts; `EvmRpcLaunchIndexer` indexes Base/BSC ERC-20 Transfer logs in bounded block chunks, checks transaction receipts for a matching native or configured quote-token spend, and reads ERC-20 `totalSupply`/`decimals` at the launch block using historical `eth_call`. This is a block-end supply snapshot, not an exact transaction-index snapshot; tokens with same-block supply mutations need transaction-level reconstruction or must remain uncertified. `HeliusNativeFundingResolver` traces inbound native-SOL transfers; `EvmQuoteFundingResolver` traces inbound transfers of explicitly configured quote-token contracts. Funding-source scope is deliberately limited (native SOL on Solana; allowlisted ERC-20 quote assets on EVM), so these traces do not prove every possible funding path. Every page/range, provider identity, token/chain, transaction reference, supply block reference and coverage boundary is retained. Pagination limits, RPC errors, missing supply, missing funder traces, rejected records or incomplete coverage force unknown bundled supply. `LaunchIntelligenceService.evaluate()` creates the launch-bundle report and automatically submits it with liquidity/developer evidence to `VerifiedIntelligenceAdapters.validate_composite_safety()`. The builder `build_launch_intelligence_service()` wires configured providers. Solana launch-slot supply is reconstructed from finalized `getTokenSupply` by reversing every post-launch-slot mint and burn in a complete Helius Parsed Events Scan; raw integer amounts and complete pagination are mandatory, and the scan shares the configured `LAUNCH_INDEX_MAX_PAGES` bound. Current supply alone is never accepted. Base/BSC need dedicated historical RPC endpoints and launch/window block bounds. The service is wired into the discovery monitor when `LAUNCH_INTELLIGENCE_ENABLED=true`; each newly discovered candidate is passed through a separately trusted origin resolver and then through the launch indexer and composite safety validator. The monitor persists the origin evidence ID, indexer coverage, bundle percentage and gate outcome as `LAUNCH_INTELLIGENCE` ledger events.\n- Launch origin discovery (`veltrix.launch_origin`): `SolanaLaunchOriginResolver` paginates Helius address history to the oldest mint-address transaction and requires a parsed SPL Token `initializeMint`/`initializeMint2` instruction for the exact mint; it refuses to guess if bounded history is exhausted. `EvmLaunchOriginResolver` locates the first block with contract code using historical `eth_getCode`, then binary-searches the first block at/after the configured launch-window end. This EVM method assumes persistent contract code and rejects addresses without current code; self-destruct/redeploy patterns and RPCs without historical state are not certified. Origin resolvers have their own allowlist (`TRUSTED_LAUNCH_ORIGIN_PROVIDERS`) separate from the launch transaction indexer allowlist.\n- LaunchBundleAnalyzer: computes a launch-window shared-funder heuristic from transaction-level token-buy evidence. It groups distinct buyer wallets by funding source, counts only launch-window token amounts, rejects wrong-chain/token rows, duplicate transactions, stale/future records and invalid amounts, and requires an explicitly trusted provider plus complete coverage and a valid total-supply denominator. Any rejected row, incomplete coverage or supply inconsistency withholds `bundled_supply_pct`; a clean complete scan with no qualifying cluster may report zero. Shared funding is not proof of developer/insider control. The analyzer is connected to the launch provider service and composite safety gate, but no candidate can pass without independently trusted liquidity and developer-holdings evidence.\n- CompositeTokenSafetyValidator: combines three claim-separated evidence streams into the typed `SafetyReport` consumed by Sniper. Liquidity-lock evidence, developer-holdings evidence and launch-bundle evidence each require their own explicit provider allowlist; the three providers must be distinct. All records must match the token, be fresh, and pass strict checks: liquidity positively locked, developer-linked holdings below 5%, and complete launch-window coverage proving exactly 0% bundled supply. Wrong-chain reports, rejected launch transactions, stale evidence, shared provider identities and unknown values fail closed. `composite_validator_from_settings()` builds the claim-specific policy from `TRUSTED_LIQUIDITY_PROVIDERS`, `TRUSTED_DEVELOPER_PROVIDERS` and `TRUSTED_BUNDLE_PROVIDERS`; the three lists must identify distinct vetted providers. `VerifiedIntelligenceAdapters` exposes this only after an operator explicitly installs that validator; the generic provider allowlist is not silently promoted into these trust roles. This is a decision gate, not an on-chain audit or guarantee of provider integrity.\n- TokenSafetyValidator: fail-closed evidence contract requiring a trusted provider, matching token address, fresh evidence, confirmed liquidity lock, developer holdings below 5%, and zero bundled supply. No provider is trusted by default.
- VerifiedIntelligenceAdapters: defines `SmartWalletProvider` and `TokenSafetyProvider` interfaces plus fail-closed collection adapters. It normalizes smart-wallet BUY observations only from operator-allowlisted providers; rejects unsupported chains, stale/future timestamps, malformed notionals, missing transaction IDs, duplicate transactions and provider-identity mismatches. Safety observations pass through the trusted-provider and freshness validator. Whale and Sniper decisions expose agent-specific rejection reasons. This is a provenance/freshness gate, not proof that a provider's claims are true; provider due diligence and actual integrations remain required.
- SQLite paper ledger: persists market observations, paper fills, positions, one-time 2x/3x exit milestones and peak prices. Fresh observed prices trigger the initial 6% stop, one-time partial profit-taking at 2x and 3x, then a 6% trailing stop on the remainder. Snapshot supports unrealized PnL/equity; session report summarizes realized PnL, closed-position win rate, best/worst trade and open positions.
- GitHub Actions: Python 3.11 compile and pytest checks.


- Static provider-readiness inventory (`veltrix.provider_readiness`): reports configured endpoints, claim-specific trust, known connector capability limits and missing provenance per chain without making network calls. It deliberately reports GoPlus liquidity evidence as incomplete and developer-linked holdings as unsupported; credentials and allowlists cannot turn those limitations into a pass. Launch-bundle readiness separately checks launch indexer, funding-trace and origin-resolver configuration/trust. This inventory is operational guidance only: actual per-token freshness, coverage and evidence are still checked by the runtime composite gate.

## Dashboard, market charts and continuous runtime

The Pump.fun-inspired mobile dashboard is served from `veltrix/dashboard_assets`
and exposes a read-only API from `veltrix/dashboard_server.py`. It includes
token/pair/interval controls, a real OHLCV candlestick + volume chart, paper
positions/trades, consensus/agent views, system health and a native SOL paper
wallet panel with fill history. Candles are sourced from GeckoTerminal,
persisted append-only, and rendered only from stored provider observations;
missing or stale data is labelled rather than fabricated.

The chart path is implemented end-to-end at the API level:
GeckoTerminal → candle validation/ingestion → persistent candle store →
authenticated `GET /api/candles` → dashboard chart payload. The live acceptance
workflow exercises a real provider request and the authenticated dashboard
HTTP endpoint, checking freshness, provenance, OHLC invariants and
`synthetic=false`.

The native SOL paper wallet stores all balances, fees and P&L as integer
lamports. It is wired into the consensus-approved paper worker and the
transaction-fenced pipeline, but remains disabled by default. The optional
`SOL_PAPER_TRADING_ENABLED` runtime setting enables simulation only; the
legacy USD paper broker and native SOL wallet cannot run simultaneously.
Live trading is rejected. A live acceptance workflow now obtains a real
DexScreener token quote and SOL/USD conversion, performs a simulated SOL
entry/exit, restarts the wallet and verifies both fills, quote provenance,
cash recovery and realized P&L. This validates quote-to-ledger accounting,
not strategy profitability or production execution.

Cloudflare hosting is split by responsibility: Workers serves static assets
and proxies allowlisted read-only API routes, while a persistent Python API
and pipeline runtime use the shared Turso database. Browser code never stores
the service bearer token; the Worker injects it server-side. The Worker has no
public `workers.dev` endpoint configured. Its bundle has passed Wrangler
dry-run validation and nine security/routing tests. Production deployment is
manual and restricted to `main`.

## Current operational blockers

- The persistent Python API host and production Turso database have not been
  provisioned or started. The systemd service template and five-minute
  GitHub Actions runner are implementation options, not proof of a running
  production worker. GitHub cron activates only after its workflow is merged
  into the default branch.
- Cloudflare production secrets, custom hostname, DNS/TLS route and Access
  authentication policy have not been configured. The deployment workflow
  fails closed unless the API origin and Cloudflare credentials are supplied.
- No production dashboard/browser session has been verified. The current live
  chart acceptance reaches the authenticated Python HTTP API using real
  provider candles, but does not constitute a deployed Cloudflare acceptance.
- Native SOL quote-to-ledger acceptance is passing; long-duration paper
  performance, strategy edge and fully operational consensus-approved
  production paper trading are not certified.
- Composite token-safety certification remains closed until independently
  trusted, complete liquidity-lock and developer-holdings evidence providers
  pass their live acceptance gates.

source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env

Configure `HELIUS_API_KEY` for Solana launch indexing and `TRACKED_SMART_WALLETS` for the separate wallet-history connector. The Helius launch provider reconstructs Solana supply at the launch slot from current finalized supply and a complete post-launch mint/burn history scan; incomplete scans withhold the supply denominator. Launch indexing uses dedicated `BASE_RPC_URL` and `BSC_RPC_URL` endpoints for historical logs, receipts and launch-block `totalSupply`; do not assume the Alchemy Transfers API supports BSC. Configure `LAUNCH_WINDOW_MS`, `LAUNCH_INDEX_MAX_PAGES`, `LAUNCH_BLOCK_CHUNK_SIZE` and `FUNDING_LOOKBACK_BLOCKS` to bound indexing. Set `TRUSTED_LAUNCH_ORIGIN_PROVIDERS` independently from `TRUSTED_BUNDLE_PROVIDERS`; origin identities are `helius-launch-origin`, `base-rpc-launch-origin` and `bsc-rpc-launch-origin`. Set `LAUNCH_INTELLIGENCE_ENABLED=true` to run origin resolution and composite-gate submission for discovered candidates. The quote-token lists are intentionally empty by default; add only verified USDC/USDT/DAI contract addresses and verify each contract address and asset identity on its chain before adding it. The Alchemy Transfers By Wallet endpoint is documented as beta and may change; its `bnb-mainnet` and `base-mainnet` network identifiers are used by the connector. Add `helius,alchemy` to `TRUSTED_WALLET_PROVIDERS` only after reviewing the wallet list and provider behavior. Configure `TRUSTED_BUNDLE_PROVIDERS` with the exact launch indexer IDs (`helius-launch`, `base-rpc-launch`, `bsc-rpc-launch`) and `TRUSTED_FUNDING_PROVIDERS` with the corresponding funding resolver IDs (`helius-funder`, `base-quote-funder`, `bsc-quote-funder`) only after validating each source and its coverage. Optionally set `DISCOVERY_ENABLED=true` to poll DexScreener's latest token profiles every cycle; configure `DISCOVERY_CHAINS` and `MAX_DISCOVERED_PER_CHAIN`. The profile endpoint is rate-limited to 60 requests/minute and does not represent all new pools. Keep `LIVE_TRADING=false`.

Start a 24-hour read-only monitoring session:
```bash

```

The new wallet connectors are library-level adapters and are not yet wired into a complete live signal-to-paper-entry pipeline. Launch origin discovery and monitor submission are implemented, but production credentials/endpoints and provider trust have not been verified in this deployment. ## Risk and data limitations
DexScreener pair snapshots do not prove liquidity is locked, developer holdings are below 5%, or bundled supply is zero. Missing safety fields must fail closed. The current implementation is not a financial recommendation and must not be used for live execution.


## Independent safety evidence certification

- Claim-scoped evidence now carries an explicit claim label, chain, completeness assertion, auditable source reference, method and provider-ownership group. The composite gate rejects evidence when any of these are absent, mismatched or incomplete. Two different provider IDs are not enough if both resolve to the same ownership group.
- Capability catalog (veltrix.providers.capabilities) separates useful signals from certifiable evidence. Current documented candidates remain non-certifying:
  - GoPlus token-locker lookup is documented for Base and BSC, and supported locker integrations are listed, but the public API reference does not document a stable response schema or prove exhaustive all-pool LP-position coverage. It remains partial.
  - GoPlus Solana token security is not a documented LP-lock inventory in this connector.
  - InsightX cluster metrics cover Solana, Base and BSC and describe shared-funding / transaction-pattern relationships with live balances. Public docs do not establish exhaustive holder coverage, complete developer identity attribution, or a coverage watermark. It remains partial, not a developer-holdings certificate.
- The GoPlus response's creator percentage and top-holder list remain context only. They cannot establish complete developer-linked wallet concentration.
- Opt-in real-provider probes live in tests/test_live_provider_acceptance.py. They issue read-only GET requests to GoPlus and InsightX, validate endpoint reachability and basic response shape, and are skipped by default. They do not certify token safety. Configure VELTRIX_RUN_LIVE_PROVIDER_ACCEPTANCE=true, the provider credentials and chain-specific acceptance token addresses to run them. A successful probe is not equivalent to a production safety certification.
- No live-provider probe was executed in this development run because production credentials and acceptance token addresses were not available. Mocked unit tests are not represented as real API acceptance.


- Developer concentration graph analyzer (`veltrix.developer_concentration`): consumes a complete holder-balance snapshot, a complete first-funder ancestry graph and independently attested deployer/creator roots. It reconciles all raw holder balances exactly to total supply, requires an explicit funding record for every holder and traversed intermediary, checks freshness and source identity, and only counts wallets whose ancestry actually reaches an attested developer root. Shared exchange/funder relationships alone do not count as developer linkage. It emits claim-scoped `SafetyEvidence` only when all coverage checks pass. This is an analysis contract, not a production holder/funding data connector; no current provider is capability-certified to supply the exhaustive inputs.


## Native holder inventory adapters

- `SolanaHolderInventoryProvider` enumerates finalized token accounts for both SPL Token and Token-2022 programs using mint filters, aggregates raw balances by owner, and requires holder-account and token-supply reads to report the same finalized context slot. The standard RPC method has no cursor pagination; hitting the configured response cap or receiving inconsistent context/supply fails closed.
- `EvmHolderInventoryProvider` supports Base and BSC. It scans ERC-20 `Transfer` logs from the verified deployment block through the RPC's finalized block in bounded ranges, validates log contract/block/transaction provenance, queries every discovered holder's `balanceOf` at that exact block, and requires the balances to reconcile exactly to `totalSupply`. It rejects RPCs without a finalized block tag, malformed or duplicate logs, caps, and reconciliation gaps.
- Factory: `build_holder_inventory_providers(settings)`; configuration: `SOLANA_RPC_URL`, `BASE_RPC_URL`, `BSC_RPC_URL`, `HOLDER_INVENTORY_MAX_ACCOUNTS`, `HOLDER_INVENTORY_MAX_LOGS`, `HOLDER_INVENTORY_MAX_HOLDERS`.
- These adapters are read-only and currently **not capability-certified**. They do not establish developer identity or funding ancestry; they provide the exhaustive holder snapshot input for the separate developer graph analyzer. No live chain response was executed in CI.


## First-funder ancestry provider

- `AlchemyBaseFundingGraphProvider` builds a bounded first-inbound-funder graph for Base using Alchemy's `alchemy_getAssetTransfers` API, including external, internal and ERC-20 transfer categories, ascending order and page-key exhaustion. It recursively queries intermediary funders, records transaction hashes, and rejects duplicate/malformed rows, incomplete pagination and ancestry wallet caps.
- Base only is enabled by the factory. Alchemy's published transfer API documents internal-transfer coverage for Base, but not BNB Smart Chain; BSC is intentionally withheld rather than certifying a graph with missing internal contract transfers. Solana native-SOL first-funder ancestry is provided by Helius Parsed Events Scan; it is bounded by aggregate page and wallet limits and does not cover every SPL-token funding path.
- Factory: `build_funding_graph_providers(settings)`; bounds: `FUNDING_GRAPH_MAX_PAGES`, `FUNDING_GRAPH_MAX_WALLETS` and `FUNDING_GRAPH_MAX_TOTAL_PAGES`.
- This adapter is not yet in the composite capability catalogue. A successful indexer response alone is not production certification; independently attested developer roots and live-provider acceptance are still required.


## Unified developer evidence orchestration

- `HeliusSolanaFundingGraphProvider` traces the earliest observed inbound native-SOL transfer for each holder and recursively for each intermediary, using Helius Parsed Events Scan with token-account history enabled. It preserves transaction signatures and provider-derived evidence IDs, exhausts pagination, and requires the provider's scan watermark to reach the requested end. Each request returns at most 100 matching transactions; a separate aggregate page budget caps total Helius/Alchemy calls across the complete ancestry graph. Parser failures, pagination bounds and unresolved history fail closed. Native-SOL ancestry is a heuristic: it does not cover every possible SPL-token funding route or prove common control.
- Base combines the existing exhaustive finalized holder inventory with `AlchemyBaseFundingGraphProvider`, which scans external, internal and ERC-20 transfers to reconstruct first-funder edges. BSC holder snapshots exist, but no complete BSC first-funder graph is enabled because the current Alchemy transfer coverage does not establish internal-transfer completeness.
- `DeveloperRootAttestation` is a typed input contract for an independent root-identity source. It requires chain/token binding, provider identity, evidence ID, observation time, explicit roots, completeness and source reference. Root providers must be separately allowlisted with `TRUSTED_DEVELOPER_ROOT_PROVIDERS`; launch-origin discovery is not silently promoted into developer identity.
- `DeveloperEvidenceOrchestrator` coordinates holder snapshots, funding ancestry and root attestations, invokes `DeveloperConcentrationAnalyzer`, and submits typed evidence to the existing composite gate only when the analyzer can emit a complete claim. The factory is `build_developer_evidence_orchestrator(settings, intelligence_adapters, audit_sink=...)`.
- `PaperBroker.record_developer_evidence` persists both accepted and rejected evidence decisions as `DEVELOPER_EVIDENCE_AUDIT` events, including provider IDs, evidence IDs, block references, source references and rejection reasons. Credentials are not written to the audit payload.
- No production developer-root attestation provider is connected, and the current capability catalogue does not certify the holder/funding graph as a developer-holdings provider. Consequently, this module is fail-closed and does not unlock Sniper or paper entries. Helius/Alchemy production responses and chain-specific acceptance coverage remain unverified.

- Developer evidence uses separate explicit allowlists: `TRUSTED_HOLDER_INVENTORY_PROVIDERS`, `TRUSTED_DEVELOPER_FUNDING_PROVIDERS` and `TRUSTED_DEVELOPER_ROOT_PROVIDERS`. These are independent from the certified claim-provider allowlist `TRUSTED_DEVELOPER_PROVIDERS`. Credentials alone never confer trust.

## Signed independent developer-root attestations

- `SignedDeveloperRootProvider` retrieves a chain/token-bound JSON envelope over HTTPS and verifies its canonical payload using Ed25519. The signed payload binds provider identity, chain, token address, root addresses, evidence ID, timestamp, complete-coverage assertion and an HTTPS source reference. Invalid signatures, stale/future timestamps, duplicate/malformed roots, oversized responses and mismatched claims are rejected.
- Configure `DEVELOPER_ROOT_ATTESTATION_URL`, `DEVELOPER_ROOT_ATTESTATION_PUBLIC_KEY` (base64-encoded raw 32-byte Ed25519 public key), and `DEVELOPER_ROOT_ATTESTATION_PROVIDER_ID`. The provider ID must also appear in `TRUSTED_DEVELOPER_ROOT_PROVIDERS`. The private signing key must remain with the independent attestation operator; never put it in this repository.
- The orchestrator fetches this signed attestation automatically when no attestation object is passed to `evaluate`. A valid signature proves that the configured source issued the payload; it does not by itself prove the source's developer-identity methodology is correct. The source must document how it independently establishes root identity and exhaustive coverage.
- The signed-root adapter does not promote chain-native deployers, mint authorities, creators or shared funders into developer identities. Those are candidate origin/control signals, not proof of developer ownership. The developer-holdings claim remains uncertified and the composite gate remains closed until the complete methodology and provider capability are independently reviewed and certified.


### Runtime orchestration

When `LAUNCH_INTELLIGENCE_ENABLED=true`, the CLI now builds the developer-evidence orchestrator with the same SQLite paper ledger used by the monitor and passes it to `MarketMonitor`. Each discovered candidate with a trusted launch-origin resolver is submitted to launch-bundle analysis and developer concentration analysis. The latter retrieves a signed developer-root attestation first; if that identity evidence is absent or invalid, it records a blocked audit and avoids spending holder/funder RPC calls. When the root attestation is valid, the orchestrator obtains the configured holder and funding snapshots, verifies their independent allowlists, analyzes concentration and submits only complete typed evidence to the composite safety gate.

The runtime records developer evidence outcomes separately from launch bundle outcomes and reports how many analyses were complete. This is still observation and certification work only: the current configuration has no certified developer claim provider or liquidity-lock provider, so composite safety remains closed and no paper positions are opened. The CLI does not claim a 24-hour trading session has begun merely because monitoring is enabled.


The static provider-readiness report now lists the exact developer-evidence prerequisites per chain: signed-root endpoint/key and trust, holder-inventory RPC and trust, funding-ancestry provider and trust, and the separate developer-claim allowlist. BSC explicitly reports that a complete first-funder ancestry provider is unavailable. These checks do not upgrade any partial connector to a certifying capability.


## Chain-specific liquidity-lock evidence

- `veltrix.liquidity_evidence` introduces a fail-closed, chain-bound LP-lock evidence contract. It requires a complete token-to-pool inventory, finalized pool snapshots, LP total supply, the exact LP-token balance held in locker custody, every lock record, active unlock timestamps, unique position IDs, and reconciliation of all recorded lock amounts to on-chain locker custody.
- A token does **not** pass because one pool is locked. Each discovered pool is checked independently. The weakest pool determines the reported locked percentage; every pool must have at least 99.99% of its LP supply in non-expired locks. LP units from different pools are never summed to create a misleading aggregate ratio. Missing pools, incomplete pagination, unknown locker addresses, expired-only positions, duplicate records, custody mismatches, and supply mismatches fail closed.
- Base candidate: UNCX Uniswap V2 locker `0xc4E637D37113192F4F1F060DaEbD7758De7F4131`, V2.1 `LOCKS/NONCE` profile. BSC candidate: UNCX PancakeSwap V2 locker `0xC765bddB93b0D1c1A88282BA0fa6B2d00E3e0c83`, kept on a separate legacy user-lock-index ABI profile. Both require an operator-pinned runtime bytecode hash and exact chain ID (Base 8453, BSC 56) verified by the RPC reader. The address list is a candidate registry, not an unconditional trust grant.
- Solana candidate: UNCX Raydium AMM V4 program `GsSCS3vPWrtJ5Y9aEVVT65fmrex5P5RGHXdZvsdbWgfo`; the public project publishes executable hash `60838187b2c2b92fc6094bba1dcc2a9607ca40f7fb0fdb9e7011e08fa0c863e9`. Solana evidence additionally requires each lock PDA to be owned by the pinned program and each custody token account to identify the expected LP mint, a supported SPL Token/Token-2022 owner, and the separately pinned locker custody authority. Other UNCX Solana programs (CP Swap, CLMM, Meteora DLMM and PumpSwap) remain unsupported until their deployed executable, account layout and custody derivations are independently pinned.
- `EvmLiquidityLockerProvider` and `SolanaLiquidityLockerProvider` are strict snapshot-reader boundaries. The reader is responsible for reading the chain ID/finalized block or slot, comparing observed deployed bytecode/program executable hashes to the operator-pinned hash, exhaustively enumerating the locker ABI/account records, and querying LP supply and custody at the same finalized state. A reader that cannot prove those properties must return incomplete evidence or raise; it must not synthesize a complete snapshot.
- `LiquidityEvidenceAnalyzer` converts a passing snapshot to claim-scoped `SafetyEvidence`. The composite gate now independently requires complete all-pool inventory metadata, equal discovered and actively locked pool counts, and at least 99.99% active locked LP in every pool. No liquidity-lock provider has been added to the production capability catalogue, and the current monitor has no certified all-pool inventory reader wired in. Therefore this implementation does **not** certify any real token, unlock Sniper, or enable paper/live entries. MarketMonitor now accepts per-chain liquidity snapshot providers, runs the analyzer, and forwards only a passing typed liquidity claim into launch/composite evaluation; it records blocked/verified status and does not forward incomplete evidence. No production RPC/indexer snapshot reader is configured or capability-certified yet. The production gate remains closed pending reviewed RPC/indexer implementations, provider ownership review, deployment hash pinning and live chain acceptance tests.

## Production read-only liquidity snapshot readers

The earlier liquidity layer accepted typed snapshot readers but did not itself acquire chain state. The following read-only RPC implementations now exist:

### Base and BSC V2 factories + UNCX lockers

- `veltrix.providers.evm_liquidity_reader.EvmV2LiquiditySnapshotReader` reads `eth_chainId`, the `finalized` block, factory bytecode, factory `PairCreated` logs from each configured deployment block, pair `token0/token1/factory`, LP `totalSupply`, locker `balanceOf`, and every current `LOCKS(index)` record at the same block number.
- Base uses the V2.1 `NONCE()` + `LOCKS(uint256)` profile. BSC uses its distinct legacy ABI: the reader exhaustively scans `onDeposit` and `onWithdraw` history, cross-checks each LP token's `getNumLocksForToken` count against the historical deposit count, then enumerates every `tokenLocks(lpToken,index)` record. This is not the Base nonce/mapping ABI. The BSC legacy getter and event signatures are grounded in the verified contract ABI. <https://www.codeslaw.app/contracts/bnbchain/0xc765bddb93b0d1c1a88282ba0fa6b2d00e3e0c83>
- Pool discovery and locker state use separate HTTPS RPC endpoints. Both endpoints must report a finalized head at or beyond the snapshot and agree on the exact finalized block hash. Runtime bytecode hashes for every factory and locker are operator-pinned; factory `PairCreated` event counts and monotonic pair indices must reconcile exactly to `allPairsLength()`. Empty code, mismatched hashes, capped logs, missing event IDs, factory mismatches and incomplete registries fail closed.
- The reader scans every configured factory, not only pools that currently have locker records. A pool with zero locker custody remains in the inventory and causes the composite lock claim to fail if it does not meet the per-pool threshold.
- Supported EVM scope is explicitly configured V2 factories that emit the canonical `PairCreated(address,address,address,uint256)` event. V3 NFT positions, Aerodrome Slipstream and non-V2 factories are not silently interpreted as V2 LP tokens. The registry-complete flag is an operator attestation that every AMM in the declared supported V2 scope is listed. If the scope is incomplete, do not set it true.
- Current UNCX deployment references list Base Uniswap V2.1 at `0xc4E637D37113192F4F1F060DaEbD7758De7F4131`, Base Sushiswap V2.0 at `0xBeddF48499788607B4c2e704e9099561ab38Aae8`, Base Aerodrome at `0x30e522deDfFE3e3d11Cd53E27d18Cd4F016eD870`, and BSC PancakeSwap V2 at `0xC765bddB93b0D1c1A88282BA0fa6B2d00E3e0c83`. The V2 reader currently supports the two Base V2 profiles and BSC legacy PancakeSwap V2 only; Aerodrome uses a separate AMM design and is not included. These addresses are discovery candidates only: runtime bytecode, constructor factory and ABI still require live verification. <https://docs.uncx.network/guides/for-projects/liquidity-lockers-v2/> <https://github.com/uncx-network/liquidity-locker-univ2-contracts>

### Solana Raydium AMM V4 + CPMM pool inventory; UNCX V4 locker

- `veltrix.providers.solana_liquidity_reader.SolanaRaydiumV4CpmmSnapshotReader` discovers Raydium AMM V4 pools (752-byte state; mint offsets 400/432; LP mint offset 464) and Raydium CPMM pools (637-byte `PoolState`; mint offsets 168/200; LP mint offset 136). It cross-checks both inventories through both RPC endpoints and includes pools whether or not a locker record exists.
- It enumerates UNCX Anchor `TokenLock` accounts by LP mint, validates the 146-byte account layout and discriminator, derives each `["uncx_locker", lock_id_le]` PDA and verifies the bump and program owner.
- It derives `["uncx_authority"]` and `["uncx_lp_vault", amm_id]` PDAs from the published program source. The SPL token vault must be owned by the classic Token Program, contain the expected LP mint, and be controlled by the derived authority. Vault balance must exactly equal the sum of current lock amounts. Pool lists, TokenLock account lists, program accounts, LP mint accounts and vault accounts are cross-checked through both configured RPC endpoints at the same finalized slot.
- The deployed upgradeable-loader ProgramData ELF hash is checked against the published UNCX verifiable-executable hash. Both Raydium AMM V4 and CPMM executable hashes must also be independently pinned. Pool and locker reads must return the same finalized slot; stale, truncated or inconsistent RPC responses fail closed.
- UNCX LP-lock evidence is implemented for Raydium AMM V4 only. The public UNCX CPMM locker repository currently does not provide the program source/account layout needed to verify its locker; every discovered CPMM pool is therefore retained with zero certified locker custody and blocks the all-pool safety claim. <https://github.com/uncx-network/raydium-cp-swap-lp-locker>

### Configuration and live acceptance

- Configure separate pool and locker RPC URLs for each chain in `.env` or GitHub Actions secrets.
- EVM factory/locker JSON registries require the exact deployment block and 64-character runtime code hash (without `0x`). The Base locker ABI profiles are `uncx-v2.1-locks-nonce` and `uncx-v2.0-locks-nonce`; BSC is `uncx-v1-token-lock-index-events`.
- Keep `BASE_LIQUIDITY_AMM_REGISTRY_COMPLETE`, `BSC_LIQUIDITY_AMM_REGISTRY_COMPLETE` and `SOLANA_LIQUIDITY_AMM_REGISTRY_COMPLETE` false until every factory/program in the declared supported scope is included. Pin both Raydium program hashes before constructing the Solana reader.
- Run the GitHub Actions workflow **Liquidity live read-only acceptance** manually with a chain and token address. It reports reader acceptance separately from the token's actual liquidity-lock safety result. A structurally valid reader can pass acceptance while the token correctly remains blocked because some pools are unlocked. Successful reports are retained as chain-specific JSON workflow artifacts with the finalized block/slot, deployment hashes, pool totals and per-pool lock ratios.
- Reader IDs are not added to `TRUSTED_LIQUIDITY_PROVIDERS` by code. Live acceptance, deployment ownership review, registry review and explicit operator trust are prerequisites. No transactions are sent.
