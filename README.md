# VELTRIX Multi-Agent Crypto

Paper-only research and monitoring system for Solana, Base and BSC. It has no wallet signing, private-key loading, swaps or live order execution. `LIVE_TRADING=true` is rejected.

## Current components
- Scout / Whale / Sniper: initial signal logic. Sniper now requires a typed, passing SafetyReport from the independent validator; raw booleans in market payloads are rejected. Whale-flow and verified launch-safety feeds are not yet connected.
- Shield: enforces at least two distinct BUY agents, a maximum $50 position and a maximum of 10 open positions.
- Exit: the SQLite paper broker persists 2x / 3x partial-profit milestones and stop/trailing-stop state across restarts; this is paper-fill simulation, not exchange execution.
- DexScreener adapter: read-only token-pair snapshots for Solana, Base and BSC.
- Helius Parsed Events connector: read-only Solana wallet swap history for configured tracked wallets, with token-mint matching, bounded pagination, successful-swap filtering and an injected spot-price resolver. The USD notional is an estimate using the current spot price, not the historical execution price.
- Alchemy Transfers By Wallet connector: read-only Base and BNB Chain (BSC) wallet transfer history using the multichain Data API. It emits a BUY only when the same transaction includes an inbound target ERC-20 and an outbound operator-allowlisted USDC/USDT/DAI transfer from the tracked wallet; plain transfers, deposits and airdrops are rejected. Quote notional treats the stablecoin quantity as an approximate USD value (not an exact historical execution valuation); depegs, fees, router behavior and provider labeling can affect it. Pagination is bounded, provider partial errors fail closed, and `alchemy` remains untrusted until explicitly allowlisted.
- Wallet provider factory: constructs Helius and/or Alchemy read-only connectors only when both the corresponding API key and tracked-wallet list are configured. It does not add either provider to the trust allowlist and does not enable trading.
- CrossChainIntelligenceCoordinator: fetches observations from trusted connectors, verifies that each response identifies the connector that returned it, rejects observations for the wrong requested chain, normalizes all providers in one pass and deduplicates by `(chain, wallet, transaction ID, token)` using case-insensitive EVM normalization and case-sensitive Solana base58 normalization. It then forms fresh multi-wallet clusters from the configured tracked-wallet allowlist and can enrich a token context for the Whale agent. Provider failures are isolated and reported without exposing credential-bearing exception details. `Core.evaluate_with_intelligence()` discards caller-supplied whale claims and accepts cluster evidence only when the coordinator result matches the token chain; Core still requires same-token consensus from at least two distinct agents.
- Optional monitor integration: when API credentials, tracked wallets and provider trust allowlists are configured, the 24-hour monitor collects verified wallet observations alongside market snapshots and reports cluster/failure counts. This remains observation-only: it does not open paper positions or send live orders.
- GoPlus token-security connector: read-only BSC (chain ID 56), Base (chain ID 8453) token-risk endpoints and authenticated Solana beta endpoint. It can only mark LP liquidity locked when the returned LP-holder list is complete and every listed holder is explicitly locked. For Base and BSC, it preserves the documented `creator_percent` fraction as a separate creator-concentration field; it does not treat this as complete developer-wallet concentration. Solana creator concentration remains unknown. Developer holdings and bundled-supply evidence remain unknown to the strict Sniper validator, so GoPlus alone cannot pass the complete Sniper gate. Base and BSC creator concentration are taken from the documented `creator_percent` field when present.
- Optional candidate discovery: consumes DexScreener's latest token-profile feed, filters to configured chains, deduplicates and caps candidate counts. This is profile/promotional discovery, not an exhaustive new-pair feed or organic trend ranking.
- WhaleFlowAggregator: clusters buys only from operator-allowlisted wallets, within a freshness window and minimum-notional threshold. A real transaction/indexer feed and vetted wallet list are still required.
- Launch Intelligence Provider Layer (`veltrix.providers.launch`): `HeliusLaunchIndexer` scans Solana launch-mint activity with Parsed Events Scan pagination, filters parsed swaps and records launch-window token receipts; `EvmRpcLaunchIndexer` indexes Base/BSC ERC-20 Transfer logs in bounded block chunks, checks transaction receipts for a matching native or configured quote-token spend, and reads ERC-20 `totalSupply`/`decimals` at the launch block using historical `eth_call`. `HeliusNativeFundingResolver` traces inbound native-SOL transfers; `EvmQuoteFundingResolver` traces inbound transfers of explicitly configured quote-token contracts. Funding-source scope is deliberately limited (native SOL on Solana; allowlisted ERC-20 quote assets on EVM), so these traces do not prove every possible funding path. Every page/range, provider identity, token/chain, transaction reference, supply block reference and coverage boundary is retained. Pagination limits, RPC errors, missing supply, missing funder traces, rejected records or incomplete coverage force unknown bundled supply. `LaunchIntelligenceService.evaluate()` creates the launch-bundle report and automatically submits it with liquidity/developer evidence to `VerifiedIntelligenceAdapters.validate_composite_safety()`. The builder `build_launch_intelligence_service()` wires configured providers. Solana historical mint supply is intentionally an injected resolver; current `getTokenSupply` is not accepted as launch-time supply. Base/BSC need dedicated historical RPC endpoints and launch/window block bounds. The service is wired into the discovery monitor when `LAUNCH_INTELLIGENCE_ENABLED=true`; each newly discovered candidate is passed through a separately trusted origin resolver and then through the launch indexer and composite safety validator. The monitor persists the origin evidence ID, indexer coverage, bundle percentage and gate outcome as `LAUNCH_INTELLIGENCE` ledger events.\n- Launch origin discovery (`veltrix.launch_origin`): `SolanaLaunchOriginResolver` paginates Helius address history to the oldest mint-address transaction and requires a parsed SPL Token `initializeMint`/`initializeMint2` instruction for the exact mint; it refuses to guess if bounded history is exhausted. `EvmLaunchOriginResolver` locates the first block with contract code using historical `eth_getCode`, then binary-searches the first block at/after the configured launch-window end. This EVM method assumes persistent contract code and rejects addresses without current code; self-destruct/redeploy patterns and RPCs without historical state are not certified. Origin resolvers have their own allowlist (`TRUSTED_LAUNCH_ORIGIN_PROVIDERS`) separate from the launch transaction indexer allowlist.\n- LaunchBundleAnalyzer: computes a launch-window shared-funder heuristic from transaction-level token-buy evidence. It groups distinct buyer wallets by funding source, counts only launch-window token amounts, rejects wrong-chain/token rows, duplicate transactions, stale/future records and invalid amounts, and requires an explicitly trusted provider plus complete coverage and a valid total-supply denominator. Any rejected row, incomplete coverage or supply inconsistency withholds `bundled_supply_pct`; a clean complete scan with no qualifying cluster may report zero. Shared funding is not proof of developer/insider control, and this analyzer is not yet connected to a production launch indexer or Sniper safety gate.\n- CompositeTokenSafetyValidator: combines three claim-separated evidence streams into the typed `SafetyReport` consumed by Sniper. Liquidity-lock evidence, developer-holdings evidence and launch-bundle evidence each require their own explicit provider allowlist; the three providers must be distinct. All records must match the token, be fresh, and pass strict checks: liquidity positively locked, developer-linked holdings below 5%, and complete launch-window coverage proving exactly 0% bundled supply. Wrong-chain reports, rejected launch transactions, stale evidence, shared provider identities and unknown values fail closed. `composite_validator_from_settings()` builds the claim-specific policy from `TRUSTED_LIQUIDITY_PROVIDERS`, `TRUSTED_DEVELOPER_PROVIDERS` and `TRUSTED_BUNDLE_PROVIDERS`; the three lists must identify distinct vetted providers. `VerifiedIntelligenceAdapters` exposes this only after an operator explicitly installs that validator; the generic provider allowlist is not silently promoted into these trust roles. This is a decision gate, not an on-chain audit or guarantee of provider integrity.\n- TokenSafetyValidator: fail-closed evidence contract requiring a trusted provider, matching token address, fresh evidence, confirmed liquidity lock, developer holdings below 5%, and zero bundled supply. No provider is trusted by default.
- VerifiedIntelligenceAdapters: defines `SmartWalletProvider` and `TokenSafetyProvider` interfaces plus fail-closed collection adapters. It normalizes smart-wallet BUY observations only from operator-allowlisted providers; rejects unsupported chains, stale/future timestamps, malformed notionals, missing transaction IDs, duplicate transactions and provider-identity mismatches. Safety observations pass through the trusted-provider and freshness validator. Whale and Sniper decisions expose agent-specific rejection reasons. This is a provenance/freshness gate, not proof that a provider's claims are true; provider due diligence and actual integrations remain required.
- SQLite paper ledger: persists market observations, paper fills, positions, one-time 2x/3x exit milestones and peak prices. Fresh observed prices trigger the initial 6% stop, one-time partial profit-taking at 2x and 3x, then a 6% trailing stop on the remainder. Snapshot supports unrealized PnL/equity; session report summarizes realized PnL, closed-position win rate, best/worst trade and open positions.
- GitHub Actions: Python 3.11 compile and pytest checks.

## Setup
Python 3.11+
```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Add comma-separated contract addresses to `WATCHLIST_SOLANA`, `WATCHLIST_BASE`, and/or `WATCHLIST_BSC`. Configure `HELIUS_API_KEY` for Solana launch indexing and `TRACKED_SMART_WALLETS` for the separate wallet-history connector. A launch-time historical Solana mint-supply resolver must be supplied by the operator; a current supply lookup is not accepted. For Base and BNB Chain, configure `ALCHEMY_API_KEY`, `TRACKED_EVM_WALLETS`, and explicit comma-separated quote-token contract addresses in `ALCHEMY_QUOTE_TOKENS_BASE` and `ALCHEMY_QUOTE_TOKENS_BSC`. Launch indexing uses dedicated `BASE_RPC_URL` and `BSC_RPC_URL` endpoints for historical logs, receipts and launch-block `totalSupply`; do not assume the Alchemy Transfers API supports BSC. Configure `LAUNCH_WINDOW_MS`, `LAUNCH_INDEX_MAX_PAGES`, `LAUNCH_BLOCK_CHUNK_SIZE` and `FUNDING_LOOKBACK_BLOCKS` to bound indexing. Set `TRUSTED_LAUNCH_ORIGIN_PROVIDERS` independently from `TRUSTED_BUNDLE_PROVIDERS`; origin identities are `helius-launch-origin`, `base-rpc-launch-origin` and `bsc-rpc-launch-origin`. Set `LAUNCH_INTELLIGENCE_ENABLED=true` to run origin resolution and composite-gate submission for discovered candidates. The quote-token lists are intentionally empty by default; add only verified USDC/USDT/DAI contract addresses and verify each contract address and asset identity on its chain before adding it. The Alchemy Transfers By Wallet endpoint is documented as beta and may change; its `bnb-mainnet` and `base-mainnet` network identifiers are used by the connector. Add `helius,alchemy` to `TRUSTED_WALLET_PROVIDERS` only after reviewing the wallet list and provider behavior. Configure `TRUSTED_BUNDLE_PROVIDERS` with the exact launch indexer IDs (`helius-launch`, `base-rpc-launch`, `bsc-rpc-launch`) and `TRUSTED_FUNDING_PROVIDERS` with the corresponding funding resolver IDs (`helius-funder`, `base-quote-funder`, `bsc-quote-funder`) only after validating each source and its coverage. The liquidity/developer provider lists remain independent and must identify distinct providers. `GOPLUS_ACCESS_TOKEN` is required for the GoPlus Solana beta endpoint; BSC uses the documented chain-ID endpoint. Optionally set `DISCOVERY_ENABLED=true` to poll DexScreener's latest token profiles every cycle; configure `DISCOVERY_CHAINS` and `MAX_DISCOVERED_PER_CHAIN`. The profile endpoint is rate-limited to 60 requests/minute and does not represent all new pools. Keep `LIVE_TRADING=false`.

Start a 24-hour read-only monitoring session:
```bash
python -m veltrix.main --hours 24
```

Market observations are saved to the SQLite database at `DB_PATH`. No positions are opened automatically: the CLI is still observation-only. The new wallet connectors are library-level adapters and are not yet wired into a complete live signal-to-paper-entry pipeline. Launch origin discovery and monitor submission are implemented, but production credentials/endpoints and provider trust have not been verified in this deployment. Enable candidate discovery and launch evaluation separately with `DISCOVERY_ENABLED=true` and `LAUNCH_INTELLIGENCE_ENABLED=true`. Configure `TRUSTED_LAUNCH_ORIGIN_PROVIDERS` with `helius-launch-origin`, `base-rpc-launch-origin`, and/or `bsc-rpc-launch-origin` only after vetting the corresponding source. The runtime currently supplies no liquidity-lock or complete developer-holdings evidence providers; therefore every candidate remains blocked by the composite safety gate and no paper entries are created. An actual trusted token-safety provider, comprehensive launch/pool discovery and end-to-end paper-session acceptance must pass before paper entries are enabled.

## Risk and data limitations
DexScreener pair snapshots do not prove liquidity is locked, developer holdings are below 5%, or bundled supply is zero. Missing safety fields must fail closed. The current implementation is not a financial recommendation and must not be used for live execution.
