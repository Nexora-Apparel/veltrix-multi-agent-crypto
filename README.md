# VELTRIX Multi-Agent Crypto

Paper-only research and monitoring system for Solana, Base and BSC. It has no wallet signing, private-key loading, swaps or live order execution. `LIVE_TRADING=true` is rejected.

## Current components
- Scout / Whale / Sniper: initial signal logic. Sniper now requires a typed, passing SafetyReport from the independent validator; raw booleans in market payloads are rejected. Whale-flow and verified launch-safety feeds are not yet connected.
- Shield: enforces at least two distinct BUY agents, a maximum $50 position and a maximum of 10 open positions.
- Exit: the SQLite paper broker persists 2x / 3x partial-profit milestones and stop/trailing-stop state across restarts; this is paper-fill simulation, not exchange execution.
- DexScreener adapter: read-only token-pair snapshots for Solana, Base and BSC.
- Helius Parsed Events connector: read-only Solana wallet swap history for configured tracked wallets, with token-mint matching, bounded pagination, successful-swap filtering and an injected spot-price resolver. The USD notional is an estimate using the current spot price, not the historical execution price.
- Alchemy Transfers By Wallet connector: read-only Base and BNB Chain (BSC) wallet transfer history using the multichain Data API. It emits a BUY only when the same transaction includes an inbound target ERC-20 and an outbound operator-allowlisted USDC/USDT/DAI transfer from the tracked wallet; plain transfers, deposits and airdrops are rejected. Quote notional treats the stablecoin quantity as an approximate USD value (not an exact historical execution valuation); depegs, fees, router behavior and provider labeling can affect it. Pagination is bounded, provider partial errors fail closed, and `alchemy` remains untrusted until explicitly allowlisted.
- Wallet provider factory: constructs Helius and/or Alchemy read-only connectors only when both the corresponding API key and tracked-wallet list are configured. It does not add either provider to the trust allowlist and does not enable trading.
- CrossChainIntelligenceCoordinator: fetches observations from trusted connectors, verifies that each response identifies the connector that returned it, rejects observations for the wrong requested chain, normalizes all providers in one pass and deduplicates by `(chain, wallet, transaction ID, token)` using case-insensitive EVM normalization and case-sensitive Solana base58 normalization. It then forms fresh multi-wallet clusters from the configured tracked-wallet allowlist and can enrich a token context for the Whale agent. Provider failures are isolated and reported without exposing credential-bearing exception details. `Core.evaluate_with_intelligence()` discards caller-supplied whale claims and accepts cluster evidence only when the coordinator result matches the token chain; Core still requires same-token consensus from at least two distinct agents.
- Optional monitor integration: when API credentials, tracked wallets and provider trust allowlists are configured, the 24-hour monitor collects verified wallet observations alongside market snapshots and reports cluster/failure counts. This remains observation-only: it does not open paper positions or send live orders.
- GoPlus token-security connector: read-only BSC (chain ID 56), Base (chain ID 8453) token-risk endpoints and authenticated Solana beta endpoint. It can only mark LP liquidity locked when the returned LP-holder list is complete and every listed holder is explicitly locked. For Base and BSC, it preserves the documented `creator_percent` fraction as a separate creator-concentration field; it does not treat this as complete developer-wallet concentration. Solana creator concentration remains unknown. Developer holdings and bundled-supply evidence remain unknown to the strict Sniper validator, so GoPlus alone cannot pass the complete Sniper gate. Base and BSC creator concentration are taken from the documented `creator_percent` field when present.
- Optional candidate discovery: consumes DexScreener's latest token-profile feed, filters to configured chains, deduplicates and caps candidate counts. This is profile/promotional discovery, not an exhaustive new-pair feed or organic trend ranking.
- WhaleFlowAggregator: clusters buys only from operator-allowlisted wallets, within a freshness window and minimum-notional threshold. A real transaction/indexer feed and vetted wallet list are still required.
- Launch Intelligence Provider Layer (`veltrix.providers.launch`): `HeliusLaunchIndexer` scans Solana launch-mint activity with Parsed Events Scan pagination, filters parsed swaps and records launch-window token receipts; `EvmRpcLaunchIndexer` indexes Base/BSC ERC-20 Transfer logs in bounded block chunks, checks transaction receipts for a matching native or configured quote-token spend, and reads ERC-20 `totalSupply`/`decimals` at the launch block using historical `eth_call`. This is a block-end supply snapshot, not an exact transaction-index snapshot; tokens with same-block supply mutations need transaction-level reconstruction or must remain uncertified. `HeliusNativeFundingResolver` traces inbound native-SOL transfers; `EvmQuoteFundingResolver` traces inbound transfers of explicitly configured quote-token contracts. Funding-source scope is deliberately limited (native SOL on Solana; allowlisted ERC-20 quote assets on EVM), so these traces do not prove every possible funding path. Every page/range, provider identity, token/chain, transaction reference, supply block reference and coverage boundary is retained. Pagination limits, RPC errors, missing supply, missing funder traces, rejected records or incomplete coverage force unknown bundled supply. `LaunchIntelligenceService.evaluate()` creates the launch-bundle report and automatically submits it with liquidity/developer evidence to `VerifiedIntelligenceAdapters.validate_composite_safety()`. The builder `build_launch_intelligence_service()` wires configured providers. Solana launch-slot supply is reconstructed from finalized `getTokenSupply` by reversing every post-launch-slot mint and burn in a complete Helius Parsed Events Scan; raw integer amounts and complete pagination are mandatory, and the scan shares the configured `LAUNCH_INDEX_MAX_PAGES` bound. Current supply alone is never accepted. Base/BSC need dedicated historical RPC endpoints and launch/window block bounds. The service is wired into the discovery monitor when `LAUNCH_INTELLIGENCE_ENABLED=true`; each newly discovered candidate is passed through a separately trusted origin resolver and then through the launch indexer and composite safety validator. The monitor persists the origin evidence ID, indexer coverage, bundle percentage and gate outcome as `LAUNCH_INTELLIGENCE` ledger events.\n- Launch origin discovery (`veltrix.launch_origin`): `SolanaLaunchOriginResolver` paginates Helius address history to the oldest mint-address transaction and requires a parsed SPL Token `initializeMint`/`initializeMint2` instruction for the exact mint; it refuses to guess if bounded history is exhausted. `EvmLaunchOriginResolver` locates the first block with contract code using historical `eth_getCode`, then binary-searches the first block at/after the configured launch-window end. This EVM method assumes persistent contract code and rejects addresses without current code; self-destruct/redeploy patterns and RPCs without historical state are not certified. Origin resolvers have their own allowlist (`TRUSTED_LAUNCH_ORIGIN_PROVIDERS`) separate from the launch transaction indexer allowlist.\n- LaunchBundleAnalyzer: computes a launch-window shared-funder heuristic from transaction-level token-buy evidence. It groups distinct buyer wallets by funding source, counts only launch-window token amounts, rejects wrong-chain/token rows, duplicate transactions, stale/future records and invalid amounts, and requires an explicitly trusted provider plus complete coverage and a valid total-supply denominator. Any rejected row, incomplete coverage or supply inconsistency withholds `bundled_supply_pct`; a clean complete scan with no qualifying cluster may report zero. Shared funding is not proof of developer/insider control. The analyzer is connected to the launch provider service and composite safety gate, but no candidate can pass without independently trusted liquidity and developer-holdings evidence.\n- CompositeTokenSafetyValidator: combines three claim-separated evidence streams into the typed `SafetyReport` consumed by Sniper. Liquidity-lock evidence, developer-holdings evidence and launch-bundle evidence each require their own explicit provider allowlist; the three providers must be distinct. All records must match the token, be fresh, and pass strict checks: liquidity positively locked, developer-linked holdings below 5%, and complete launch-window coverage proving exactly 0% bundled supply. Wrong-chain reports, rejected launch transactions, stale evidence, shared provider identities and unknown values fail closed. `composite_validator_from_settings()` builds the claim-specific policy from `TRUSTED_LIQUIDITY_PROVIDERS`, `TRUSTED_DEVELOPER_PROVIDERS` and `TRUSTED_BUNDLE_PROVIDERS`; the three lists must identify distinct vetted providers. `VerifiedIntelligenceAdapters` exposes this only after an operator explicitly installs that validator; the generic provider allowlist is not silently promoted into these trust roles. This is a decision gate, not an on-chain audit or guarantee of provider integrity.\n- TokenSafetyValidator: fail-closed evidence contract requiring a trusted provider, matching token address, fresh evidence, confirmed liquidity lock, developer holdings below 5%, and zero bundled supply. No provider is trusted by default.
- VerifiedIntelligenceAdapters: defines `SmartWalletProvider` and `TokenSafetyProvider` interfaces plus fail-closed collection adapters. It normalizes smart-wallet BUY observations only from operator-allowlisted providers; rejects unsupported chains, stale/future timestamps, malformed notionals, missing transaction IDs, duplicate transactions and provider-identity mismatches. Safety observations pass through the trusted-provider and freshness validator. Whale and Sniper decisions expose agent-specific rejection reasons. This is a provenance/freshness gate, not proof that a provider's claims are true; provider due diligence and actual integrations remain required.
- SQLite paper ledger: persists market observations, paper fills, positions, one-time 2x/3x exit milestones and peak prices. Fresh observed prices trigger the initial 6% stop, one-time partial profit-taking at 2x and 3x, then a 6% trailing stop on the remainder. Snapshot supports unrealized PnL/equity; session report summarizes realized PnL, closed-position win rate, best/worst trade and open positions.
- GitHub Actions: Python 3.11 compile and pytest checks.


- Static provider-readiness inventory (`veltrix.provider_readiness`): reports configured endpoints, claim-specific trust, known connector capability limits and missing provenance per chain without making network calls. It deliberately reports GoPlus liquidity evidence as incomplete and developer-linked holdings as unsupported; credentials and allowlists cannot turn those limitations into a pass. Launch-bundle readiness separately checks launch indexer, funding-trace and origin-resolver configuration/trust. This inventory is operational guidance only: actual per-token freshness, coverage and evidence are still checked by the runtime composite gate.

## Setup
Python 3.11+
```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Add comma-separated contract addresses to `WATCHLIST_SOLANA`, `WATCHLIST_BASE`, and/or `WATCHLIST_BSC`. Configure `HELIUS_API_KEY` for Solana launch indexing and `TRACKED_SMART_WALLETS` for the separate wallet-history connector. The Helius launch provider reconstructs Solana supply at the launch slot from current finalized supply and a complete post-launch mint/burn history scan; incomplete scans withhold the supply denominator. For Base and BNB Chain, configure `ALCHEMY_API_KEY`, `TRACKED_EVM_WALLETS`, and explicit comma-separated quote-token contract addresses in `ALCHEMY_QUOTE_TOKENS_BASE` and `ALCHEMY_QUOTE_TOKENS_BSC`. Launch indexing uses dedicated `BASE_RPC_URL` and `BSC_RPC_URL` endpoints for historical logs, receipts and launch-block `totalSupply`; do not assume the Alchemy Transfers API supports BSC. Configure `LAUNCH_WINDOW_MS`, `LAUNCH_INDEX_MAX_PAGES`, `LAUNCH_BLOCK_CHUNK_SIZE` and `FUNDING_LOOKBACK_BLOCKS` to bound indexing. Set `TRUSTED_LAUNCH_ORIGIN_PROVIDERS` independently from `TRUSTED_BUNDLE_PROVIDERS`; origin identities are `helius-launch-origin`, `base-rpc-launch-origin` and `bsc-rpc-launch-origin`. Set `LAUNCH_INTELLIGENCE_ENABLED=true` to run origin resolution and composite-gate submission for discovered candidates. The quote-token lists are intentionally empty by default; add only verified USDC/USDT/DAI contract addresses and verify each contract address and asset identity on its chain before adding it. The Alchemy Transfers By Wallet endpoint is documented as beta and may change; its `bnb-mainnet` and `base-mainnet` network identifiers are used by the connector. Add `helius,alchemy` to `TRUSTED_WALLET_PROVIDERS` only after reviewing the wallet list and provider behavior. Configure `TRUSTED_BUNDLE_PROVIDERS` with the exact launch indexer IDs (`helius-launch`, `base-rpc-launch`, `bsc-rpc-launch`) and `TRUSTED_FUNDING_PROVIDERS` with the corresponding funding resolver IDs (`helius-funder`, `base-quote-funder`, `bsc-quote-funder`) only after validating each source and its coverage. The liquidity/developer provider lists remain independent and must identify distinct providers. `GOPLUS_ACCESS_TOKEN` is required for the GoPlus Solana beta endpoint; BSC uses the documented chain-ID endpoint. Optionally set `DISCOVERY_ENABLED=true` to poll DexScreener's latest token profiles every cycle; configure `DISCOVERY_CHAINS` and `MAX_DISCOVERED_PER_CHAIN`. The profile endpoint is rate-limited to 60 requests/minute and does not represent all new pools. Keep `LIVE_TRADING=false`.

Start a 24-hour read-only monitoring session:
```bash
python -m veltrix.main --hours 24
```

Market observations are saved to the SQLite database at `DB_PATH`. No positions are opened automatically: the CLI is still observation-only. The new wallet connectors are library-level adapters and are not yet wired into a complete live signal-to-paper-entry pipeline. Launch origin discovery and monitor submission are implemented, but production credentials/endpoints and provider trust have not been verified in this deployment. Enable candidate discovery and launch evaluation separately with `DISCOVERY_ENABLED=true` and `LAUNCH_INTELLIGENCE_ENABLED=true`. Configure `TRUSTED_LAUNCH_ORIGIN_PROVIDERS` with `helius-launch-origin`, `base-rpc-launch-origin`, and/or `bsc-rpc-launch-origin` only after vetting the corresponding source. The runtime currently supplies no liquidity-lock or complete developer-holdings evidence providers; therefore every candidate remains blocked by the composite safety gate and no paper entries are created. Solana mint-origin discovery is limited to the oldest retained signature history; when the configured page bound is reached before history exhaustion, origin is withheld. An actual trusted token-safety provider, comprehensive launch/pool discovery and end-to-end paper-session acceptance must pass before paper entries are enabled.

## Risk and data limitations
DexScreener pair snapshots do not prove liquidity is locked, developer holdings are below 5%, or bundled supply is zero. Missing safety fields must fail closed. The current implementation is not a financial recommendation and must not be used for live execution.


## Independent safety evidence certification

- Claim-scoped evidence now carries an explicit claim label, chain, completeness assertion, auditable source reference, method and provider-ownership group. The composite gate rejects evidence when any of these are absent, mismatched or incomplete. Two different provider IDs are not enough if both resolve to the same ownership group.
- Capability catalog (veltrix.providers.capabilities) separates useful signals from certifiable evidence. Current documented candidates remain non-certifying:
  - GoPlus token-locker lookup is documented for Base and BSC, and supported locker integrations are listed, but the public API reference does not document a stable response schema or prove exhaustive all-pool LP-position coverage. It remains partial.
  - GoPlus Solana token security is not a documented LP-lock inventory in this connector.
  - InsightX cluster metrics cover Solana, Base and BSC and describe shared-funding / transaction-pattern relationships with live balances. Public docs do not establish exhaustive holder coverage, complete developer identity attribution, or a coverage watermark. It remains partial, not a developer-holdings certificate.
- The GoPlus response's creator percentage and top-holder list remain context only. They cannot establish complete developer-linked wallet concentration.
- Opt-in real-provider probes live in tests/test_live_provider_acceptance.py. They issue read-only GET requests to GoPlus and InsightX, validate endpoint reachability and basic response shape, and are skipped by default. They do not certify token safety. Configure VELTRIX_RUN_LIVE_PROVIDER_ACCEPTANCE=true, the provider credentials and chain-specific acceptance token addresses to run them. A successful probe is not equivalent to a production safety certification.
- No live-provider probe was executed in this development run because production credentials and acceptance token addresses were not available. Mocked unit tests are not represented as real API acceptance.


- Developer concentration graph analyzer (`veltrix.developer_concentration`): consumes a complete holder-balance snapshot, a complete first-funder ancestry graph and independently attested deployer/creator roots. It reconciles all raw holder balances exactly to total supply, requires an explicit funding record for every holder and traversed intermediary, checks freshness and source identity, and only counts wallets whose ancestry actually reaches an attested developer root. Shared exchange/funder relationships alone do not count as developer linkage. It emits claim-scoped `SafetyEvidence` only when all coverage checks pass. This is an analysis contract, not a production holder/funding data connector; no current provider is capability-certified to supply the exhaustive inputs.


## Native holder inventory adapters

- `SolanaHolderInventoryProvider` enumerates finalized token accounts for both SPL Token and Token-2022 programs using mint filters, aggregates raw balances by owner, and requires holder-account and token-supply reads to report the same finalized context slot. The standard RPC method has no cursor pagination; hitting the configured response cap or receiving inconsistent context/supply fails closed.
- `EvmHolderInventoryProvider` supports Base and BSC. It scans ERC-20 `Transfer` logs from the verified deployment block through the RPC's finalized block in bounded ranges, validates log contract/block/transaction provenance, queries every discovered holder's `balanceOf` at that exact block, and requires the balances to reconcile exactly to `totalSupply`. It rejects RPCs without a finalized block tag, malformed or duplicate logs, caps, and reconciliation gaps.
- Factory: `build_holder_inventory_providers(settings)`; configuration: `SOLANA_RPC_URL`, `BASE_RPC_URL`, `BSC_RPC_URL`, `HOLDER_INVENTORY_MAX_ACCOUNTS`, `HOLDER_INVENTORY_MAX_LOGS`, `HOLDER_INVENTORY_MAX_HOLDERS`.
- These adapters are read-only and currently **not capability-certified**. They do not establish developer identity or funding ancestry; they provide the exhaustive holder snapshot input for the separate developer graph analyzer. No live chain response was executed in CI.


## First-funder ancestry provider

- `AlchemyBaseFundingGraphProvider` builds a bounded first-inbound-funder graph for Base using Alchemy's `alchemy_getAssetTransfers` API, including external, internal and ERC-20 transfer categories, ascending order and page-key exhaustion. It recursively queries intermediary funders, records transaction hashes, and rejects duplicate/malformed rows, incomplete pagination and ancestry wallet caps.
- Base only is enabled by the factory. Alchemy's published transfer API documents internal-transfer coverage for Base, but not BNB Smart Chain; BSC is intentionally withheld rather than certifying a graph with missing internal contract transfers. Solana funding ancestry remains unimplemented.
- Factory: `build_funding_graph_providers(settings)`; bounds: `FUNDING_GRAPH_MAX_PAGES`, `FUNDING_GRAPH_MAX_WALLETS`.
- This adapter is not yet in the composite capability catalogue. A successful indexer response alone is not production certification; independently attested developer roots and live-provider acceptance are still required.


## Unified developer evidence orchestration

- `HeliusSolanaFundingGraphProvider` traces the earliest observed inbound native-SOL transfer for each holder and recursively for each intermediary, using Helius Parsed Events Scan with token-account history enabled. It preserves transaction signatures and provider-derived evidence IDs, exhausts pagination, and requires the provider's scan watermark to reach the requested end. Parser failures, pagination bounds and unresolved history fail closed. Native-SOL ancestry is a heuristic: it does not cover every possible SPL-token funding route or prove common control.
- Base combines the existing exhaustive finalized holder inventory with `AlchemyBaseFundingGraphProvider`, which scans external, internal and ERC-20 transfers to reconstruct first-funder edges. BSC holder snapshots exist, but no complete BSC first-funder graph is enabled because the current Alchemy transfer coverage does not establish internal-transfer completeness.
- `DeveloperRootAttestation` is a typed input contract for an independent root-identity source. It requires chain/token binding, provider identity, evidence ID, observation time, explicit roots, completeness and source reference. Root providers must be separately allowlisted with `TRUSTED_DEVELOPER_ROOT_PROVIDERS`; launch-origin discovery is not silently promoted into developer identity.
- `DeveloperEvidenceOrchestrator` coordinates holder snapshots, funding ancestry and root attestations, invokes `DeveloperConcentrationAnalyzer`, and submits typed evidence to the existing composite gate only when the analyzer can emit a complete claim. The factory is `build_developer_evidence_orchestrator(settings, intelligence_adapters, audit_sink=...)`.
- `PaperBroker.record_developer_evidence` persists both accepted and rejected evidence decisions as `DEVELOPER_EVIDENCE_AUDIT` events, including provider IDs, evidence IDs, block references, source references and rejection reasons. Credentials are not written to the audit payload.
- No production developer-root attestation provider is connected, and the current capability catalogue does not certify the holder/funding graph as a developer-holdings provider. Consequently, this module is fail-closed and does not unlock Sniper or paper entries. Helius/Alchemy production responses and chain-specific acceptance coverage remain unverified.
